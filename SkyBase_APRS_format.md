# SkyBase APRS message specification

SkyBase sends positions from the SkyBase iOS app or a connected SkyBase Vario to
the SkyBase backend. The backend validates and rate-controls the positions and
forwards them to OGN over one central persistent APRS-IS connection. iPhones do
not open individual connections to OGN.

## 1 Identifiers and transport

SkyBase uses the following fixed identifiers:

* APRS source and APRS-IS login: `SKYBASE`
* TOCALL: `OGSKYB`
* software identifier in the APRS-IS login: `SKYBASE 1.0`

The backend login has this form:

```
user SKYBASE pass <passcode> vers SKYBASE 1.0
```

Messages generated by the backend use `TCPIP*`. OGN/APRS-IS may add its normal
q-construct after accepting a packet.

`OGSKYB` identifies version 1 of this format. SkyBase does not currently append
a version suffix to the TOCALL.

## 2 Position message

SkyBase emits only complete TNC2 position lines in this form:

```
SKYBASE>OGSKYB,TCPIP*:/<timestamp>h<latitude>/<longitude>'[<course>/<speed>][/A=<altitude>] id<identifier>[ <climb>fpm]
```

Parameters:

* **timestamp** — UTC time in `HHMMSS` form.
* **latitude** — uncompressed APRS latitude in `DDMM.mmN` or `DDMM.mmS` form.
* **longitude** — uncompressed APRS longitude in `DDDMM.mmE` or `DDDMM.mmW` form.
  SkyBase uses the `/` symbol table and the `'` aircraft symbol.
* **course** — optional three-digit ground track in degrees. It is present only
  when ground speed is also available. Due north is encoded as `360`; `000` is
  not used for a known course.
* **speed** — optional three-digit ground speed in knots, present together with
  course.
* **altitude** — optional GNSS altitude in feet, rounded to six unsigned digits
  as specified for `/A=`. An altitude which cannot be represented by that field
  is omitted.
* **identifier** — OGN detail byte followed by the six-hex-digit SkyBase address,
  as described in section 3.
* **climb** — optional signed vertical speed in feet per minute.

SkyBase does not send W/DAO precision, radio signal measurements, turn rate,
satellite status, device status, names, registrations or proprietary extensions.
Absent optional source values are omitted rather than synthesized.

## 3 Aircraft type and identity

Both SkyBase identity modes use OGN aircraft type `7` (paraglider), no stealth
flag and no no-track flag. The low two bits of the detail byte contain the OGN
address type. Addresses are randomly allocated from `000001` through `FFFFFE`;
the backend prevents collisions between both modes.

### 3.1 Anonymous

Anonymous sharing is the default after the user opts in.

* OGN address type: `0` (random)
* OGN detail byte: `1C`
* APRS comment identifier: `id1Cxxxxxx`
* OGN-style identifier: `RNDxxxxxx`

The random 24-bit address remains stable for one device while the same consent
period continues. It is discarded after consent is revoked and is not intended
for DDB identification.

### 3.2 Identifiable

Identifiable sharing requires a separate, explicit user selection.

* OGN address type: `3` (OGN)
* OGN detail byte: `1F`
* APRS comment identifier: `id1Fxxxxxx`
* OGN-style identifier: `OGNxxxxxx`

The randomly allocated 24-bit address is persistent for the opaque SkyBase
subject and remains stable across app and backend restarts. The six hexadecimal
digits may optionally be registered in the OGN Device Database. Registration is
not required for transmission.

The address type is a backend configuration value so that a future type assigned
to SkyBase can be adopted. SkyBase currently uses only the protocol-defined type
`3` for identifiable mode and does not claim a new address type.

## 4 Privacy and consent

Position transmission is possible only after the user explicitly enables
"Share position in the OGN network". The user can then keep the default anonymous
mode or deliberately select identifiable mode. Consent is stored and checked by
the SkyBase backend and is checked again immediately before a network write.

Neither the 24-bit address nor the APRS message contains a name, email address,
Apple ID, SkyBase account ID, phone identifier or iPhone MAC address. SkyBase does
not automatically create or update a DDB entry.

## 5 Rate control, freshness and reconnect behaviour

The central backend implements the following transmission policy:

* the first current valid position after the central connection is available is
  eligible immediately;
* subsequent packets for the same user have a minimum interval of 5 seconds;
* with the current configuration, no distance or course-change trigger is
  enabled, so continuously supplied positions are sent at the 30-second maximum
  interval;
* fixes older than 15 seconds, more than 5 seconds in the future or with horizontal
  accuracy worse than 100 metres are rejected;
* a queued packet older than 15 seconds is discarded before writing;
* repeated update UUIDs and non-increasing timestamps are rejected;
* the bounded queue retains only the latest packet per user. Positions received
  while disconnected are not queued, and pending packets are cleared on disconnect,
  so reconnect cannot replay a historical track.

The backend reconnects with exponential backoff starting at one second, doubling
to a maximum of 60 seconds, with 20% jitter. The backoff returns to one second
after a connection has remained established for 30 seconds. Only a newly received,
current position can be sent after reconnect.

The authenticated SkyBase position endpoint also applies a token bucket of five
requests per second with a burst of ten independently per subject, device and
client IP. This input limit does not bypass the per-user OGN transmission schedule.

## 6 Examples

Identifiable mode (packet already accepted and processed during SkyBase integration
testing):

```
SKYBASE>OGSKYB,TCPIP*:/130807h4704.15N/01526.89E'/A=001188 id1FFE221D
```

Anonymous mode with all implemented optional motion fields present:

```
SKYBASE>OGSKYB,TCPIP*:/130837h4704.16N/01526.90E'123/018/A=001201 id1C97DDFD +120fpm
```
